# Pitch Strategy

Use when the product sentence stabilizes; do not wait until the final hour.

## Story structure

Create `PITCH.md` to fit the exact official duration:

1. **Hook:** concrete user moment or surprising consequence.
2. **Problem:** who experiences it and why current options fail.
3. **Product reveal:** one-sentence memory hook.
4. **Live demo:** Golden Path and wow moment.
5. **Technology:** the real contribution and hardest problem solved.
6. **Impact:** credible outcome or measurable potential; do not fabricate metrics.
7. **Differentiation:** observable reason this is not the obvious/common solution.
8. **Close:** repeat the memory hook and desired future.

Slides support transitions, diagrams, and evidence; they do not replace the product. Prefer showing the action over describing a feature.

## Timing

Budget explicit seconds for each section and leave 5-10% buffer. Rehearse aloud. If over time, cut context and secondary features before the Golden Path or close.

Use one claim per sentence. Avoid feature lists, architecture jargon before the problem is clear, and long team introductions. State what the team built during the event.

## Claims and proof

For every important claim, identify proof available to judges:

- live behavior;
- before/after comparison;
- source or dataset;
- measured latency/accuracy/time saved with methodology;
- architecture or code path;
- honest limitation.

Distinguish actual results from targets. If a number is an estimate, say so.

## Handoff into demo

The speaker should know the exact sentence that triggers each click. Keep cursor movement, typing, scrolling, and window switching minimal. Use realistic preloaded data and keep an architecture diagram, screenshots, and backup video one action away.

## Final rehearsal

Run the pitch with the actual demo machine, resolution, accounts, and network. Record one rehearsal and remove dead time, repeated claims, unclear transitions, and any step that depends on luck.
